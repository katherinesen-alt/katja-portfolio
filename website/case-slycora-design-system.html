I designed the rules once, and both the interface and the AI follow them.

Slycora is a day planner for people with ADHD. The iOS app was already working when I started, but it had grown screen by screen. Buttons, spacing and colors were repeated in slightly different ways, and I had no shared place to describe them.

I built that place. It is a token file, a component library in code, a library website and a decision log. Then I wrote the rules that tell Claude Code how to work inside it. I don't write Swift, Claude Code does. The system is how I tell it what to build.

Who does what

I am the only designer. I designed the system, built the library, and shipped design changes into the app through Claude Code. I also use AI for audits, research and the decision log, but every decision and every approval is mine.

Me

System architecture, tokens, components, library pages, rules for AI, the decision log, and the design work in the app itself.

Claude Code

Writes the Swift, HTML and CSS, runs the build script, and updates the library and logs, working inside the rules in CLAUDE.md.

Developers

The developers and the architecture engineer own the backend and the technical side. They review and approve my changes. They also set up the library's domain and sign-in. For them the library is a reference, and none of their code depends on it yet.

One source of truth, and it is the code

This project has no Figma file, by design. In my earlier work the Figma library was the source of truth and the code followed it. Here the order is reversed: the source of truth is the live code. The library reads its snippets straight from the app's Swift files on every build, so it cannot drift from the product. A design file can.

build.pyOne script, run after every change
Two outputsCSS for the library, SlycoraTokens.swift for the app
Components27 Swift files in the components folder, each mirrored in HTML

Generated files are never edited by hand.

Tokens work in three layers. The first holds raw values: eight neutrals, iOS colors, and four brand colors in five steps each. The second holds roles such as text, background, border, action, status, effort and tile. Each role points to a raw value for light and for dark mode. The third holds foundations: type styles, spacing, radii, shadows and motion. Components may use roles only. This is the rule that lets the interface be recolored without touching components.

// tokens/semantic.json
"text": {
  "secondary": { "light": "neutral.700", "dark": "neutral.700",
                 "opacity": 0.75, "usage": "Captions and explanations" }
}

// generated into SlycoraTokens.swift
static let textSecondary = dynamic(light: 0x171717, lightAlpha: 0.75,
                                   dark: 0xFFFFFF, darkAlpha: 0.75)

A role in the token file, and the Swift constant that build.py generates from it.

Components follow one rule: something becomes a component only if it repeats, has states, and iOS does not provide it. Otherwise it is a style or a native element. The Button is the clearest case. The original app had eleven button styles. Now there is one component with two independent settings, importance (Primary, Secondary, Tertiary) and meaning (Default, Success, Danger, Warning), plus size, icon and loading.

struct SlycoraButton: View {
    enum Kind { case primary, secondary, tertiary }
    enum Tone { case `default`, success, danger, warning }
    enum Size { case large, small }
    ...
}

From SlycoraButton.swift. The comment above it says: "Colors come only from the semantic roles in SlycoraTokens.Colors."

From a request to a screen

Every change starts as a request in plain words: a screen, a behavior or a value I want different. Here is one about the Agenda, translated and edited for clarity:

Add a time view to Agenda: one day at a time, as time slots, based on the reference [image]. Keep our style and leave out the extra details from the reference. The height of each slot must match the duration of its task. Also replace the plus buttons in Agenda with the style from the second reference [image].

Claude Code asks questions about its plan before it writes any code. Then it reads the rules in CLAUDE.md and makes the change in the app's Swift code and, when a token is involved, in the token files. It runs build.py, which regenerates the library's CSS and SlycoraTokens.swift from the same tokens, and updates the library page and the decision log. Finally it reports what changed in the app and in the library. I review the result in the simulator and in the library, and either approve it or send the next request.

In the library, this request produced a new Agenda timeline page with variants: normal, Focus, a task without time, time that has passed, and a calendar event. The Day header page was updated, and the code and the used-in lists were regenerated from the Swift files. process.md got an entry with the reason for a timeline and the options I rejected: a full week grid, a List and Timeline segmented switch, and long empty hours.

The new library page: a live preview of the variant and the snippet that shows how to place it.

Rules for AI: how I keep it from averaging my work

A language model takes everything it knows and averages it into what it thinks is the best option. This is why AI design and AI text so often look the same. I wanted the opposite: work done the way I do it, in my style, inside the brand and common UX practice. These rules did not come from one mistake. They come from my experience of working with LLMs, and everything else stands on them.

Claude Code reads one Markdown file, CLAUDE.md, before it works. I use it to say what the system is, where its source of truth lives, and what the AI must ask me before it acts.

Tokens are stored only in design/library/tokens. CSS and Swift files are created from it by a script, I do not edit them by hand.

Prevents values that drift apart. The AI cannot fix a color in one screen and leave the library different.

Components use only roles from semantic.json, not palettes directly.

Prevents hard-coded colors. A role can be changed once for the whole app. A raw color cannot.

When I change a component, change it in two places: in Swift in the sandbox and in HTML in the library. They must always look the same. After changes, remind me what changed in both places.

Prevents a library that stops matching the app. This happened several times before the rule existed: previews no longer matched the real screen.

Before a big change, say briefly what you are going to change and wait for my ok. Do not change work with the server and data without my explicit request.

Prevents surprise rewrites, and changes to server and data work, which is not part of a design task.

In process.md keep only important product decisions. Write why it was accepted. If a decision changes, edit the existing entry, do not add a new one at the end.

Prevents a log nobody can read. The old log had grown to 330 KB and 152 sections. I cut it down, and this rule keeps it short.

Run git only when I ask. Push only to a separate branch, never to main.

Prevents anything reaching a shared repository without me knowing.

What works and where it goes next

I use the library every day and work in the iOS simulator, so I see the result of my decisions at once. I can tell right away what is technically impossible, and I no longer spend time on prototypes. The work became easier for me and for the developers, and noticeably faster, because I describe a change once and it reaches the app, the library and the log together.

What I want to build next is a living system: the AI itself notices that something needs fixing and sends me reports, or requests when my judgment is needed.
